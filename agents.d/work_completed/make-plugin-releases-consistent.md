# Make Plugin Releases Consistent

**Work card protocol: 2**

## Goal
Fix the release process so every intended plugin, including `com.zegreatrob.tools.dashboard-test-summary`, is released consistently with the project's version and release policy.

## Constraints and acceptance evidence
- Do not publish or backfill historical versions.
- Trace how plugin versions are selected and how each plugin marker and artifact enters the release workflow.
- Identify why the dashboard plugin was omitted from the `3.8.x` releases, and fix the release process so the same omission cannot recur.
- Verify the release configuration covers every intended plugin consistently, including the dashboard test summary plugin.
- Add or update automated checks for release coverage where practical. Demonstrate that the check catches a missing plugin before the fix and passes with the fix.
- Use a dry run or equivalent evidence to confirm the corrected process would release the intended plugins at the same version. Do not publish as part of this work unless separately authorized.

## Incident timeline

- **Nov 10 — plugin added** (`0fb9b14a`): Dashboard Test Summary was first added under `tools/`.
- **Nov 11 — moved to a separate included build** (`f5fa522f`): The plugin moved to `tools-plugins/` so participating builds could consume it through the composite. Its old build applied `com.zegreatrob.tools.plugins.jvm` and `com.zegreatrob.tools.plugins.publish`, which supplied the `com.zegreatrob.tools` group and Maven publication conventions. The move replaced those with plain Kotlin/JVM and Plugin Portal plugins, but did not set the group in the new build. A work note mentioned assigning a group to `tools-plugins`; that step was missed.
- **Nov 11 — original release omission found** (`fa293545`): Root `release` depended on `tools:release` and `command-line-tools:release`, but not the separate `tools-plugins` build. A direct dependency on `:tools-plugins:dashboard-test-summary:publishPlugins` was added for stable releases.
- **Nov 12 — release task generalized** (`9b4981a4`): The project-specific task path was replaced with `tools-plugins:release`, an aggregate that discovers the build's `publishPlugins` tasks. The root stable release now invokes this aggregate.
- **Nov 12 — first validation and closeout were insufficient**: A `3.8.6` dry run showed the expected task graph and version, and the build checks passed. The card was marked complete without checking the real post-release Portal metadata or the generated implementation POM. A task graph proves scheduling, not publication or public availability.
- **Nov 12 — successful stable release still not visible**: GitHub Actions run [43271856123](https://github.com/robertfmurdock/ze-great-tools/actions/runs/43271856123) calculated `3.8.7`, ran `:tools-plugins:dashboard-test-summary:publishPlugins` and `:tools-plugins:release`, and completed successfully. The same run published the other Portal plugins at `3.8.7`. Dashboard's public Portal metadata remained at `3.7.3`.
- **Nov 12 — coordinate mismatch corrected** (`a3e3e75d`): Dashboard's `3.7.3` marker POM points to `com.zegreatrob.tools:dashboard-test-summary:3.7.3`; the pre-correction `3.8.7` implementation POM generated by the build used `tools-plugins:dashboard-test-summary:3.8.7`. Setting `group` on the included-build root alone did not change the child project's group. The fix sets the root group to `com.zegreatrob.tools` and explicitly propagates it to subprojects.

## Mistakes and lessons

- Moving a publishing project to a separate included build changed its default project group. The team preserved the source and plugin ID but not the published implementation coordinates.
- The first release fix patched one project path into the root release rather than giving the included build a release entry point. The aggregate task is now the extension point for Portal plugins in that build.
- The first follow-up verified `-Pversion` and task selection but did not inspect the generated POM. Group is a per-project value; setting it on a build root does not make subprojects inherit it.
- A green `publishPlugins` task and successful GitHub release are not proof that a version is publicly resolvable. Portal publication, Maven Central publication, and Portal approval/visibility are distinct outcomes.
- The original closeout overstated what the evidence established. Future release fixes must verify generated marker and implementation coordinates before release, then verify public Portal metadata after release.

Check the publisher account and email before attempting another publication; do not retry or backfill `3.8.7`.

This records CI success only; it does not establish that a stable `3.8.8` Portal publication occurred or is visible. Confirm Portal visibility after a later authorized stable release.
